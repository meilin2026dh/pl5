# V3.7.5 Scientific Question Engine — Design

## Purpose
Advance PL5 from rule-triggered experiments into an auditable problem-oriented research loop. The system shall record what was observed, formulate multiple falsifiable causal explanations, select a discriminating *new* experiment, execute it through the existing V3.7.4 bounded engine, record contrary evidence, and choose another question. Results are synthetic mathematical reconstruction only; no lottery edge claims.

## Status and constraints
V3.7.4 already supplies a deterministic finite search engine, train/holdout split, frozen operator evaluation, per-cycle protocol, journal persistence and shared `.run.lock`. V3.7.5 must build on it rather than fork its search implementation. User has authorized direct experimentation. No LLM, network, self-modifying executable code, wager placement, unattended cloud daemon, or access to real sensitive data. Existing V3.7.4 runs remain byte-for-byte untouched.

## Options considered
1. **Add a question layer around the existing controller (selected):** bounded, testable, reuses models and evidentiary safeguards. Can choose new scientific focus without modifying candidate search.
2. Replace V3.7.4 with a free-form LLM scientist: unbounded costs, poor reproducibility, possible unsafe autogenerated code.
3. Append additional static anomaly tags: cheap but fails requirement to generate explicit hypotheses, discriminating experiments and question hierarchy.

## Scientific problem cycle
1. Scan all committed cycle results and state; derive stable parent/child scientific questions from *observed* failures (not arbitrary extra claims). Distinguish null-control coincidences, true out-of-sample generalization gaps, weak structural recovery, and research-mechanism uncertainty.
2. Each question contains problem ID, parent discipline, observation, competing hypotheses, test that would count against each hypothesis, evidence link, status, impact/novelty/information-value/cost-based *planning* priority (never model confidence), follow-up count and stop rule.
3. Choose next question by priority and investigation quota. Emit immutable pre-experiment plan with a chosen hypothesis/intervention, fresh seed, target synthetic task, budget and experiment limitations before invoking search.
4. Use the same locked V3.7.4 experiment runner, but allow a preregistered `focus_case` to override heuristic task selection while periodic independent random controls remain mandatory. Carry question ID and plan SHA into the original cycle protocol.
5. After all frozen fits have been scored, update question ledger from immutable result files; summarize supporting/contrary evidence, and either schedule a fresh experiment, mark unresolved/exhausted, or change focus. Never call a single positive result a proof.
6. Recovery reconciles existing pending plans with prior history rather than rewriting frozen protocols or repeating completed cycles.

## Non-goals and limits
Not a self-authoring code agent. A selected experiment can distinguish hypotheses only within predeclared task families and policies. No claim of novel mathematical theorem or transferable lottery filtering. The registry records scientific *candidates*, not established truths.

## Acceptance
- Tests verify historical null and structured observations lead to different question types with at least two competing hypotheses.
- A chosen focus changes the actual next protocol, while compulsory periodic null controls remain in place.
- Boundaries for duplicate state, invalid cases, concurrent runs, incomplete resume, and locked plans reject safely.
- Search budget and train/holdout isolation stay exactly as V3.7.4; no inference uses an unseen label before a candidate is frozen.
- An actual continuation from 8 existing rounds produces independently seeded new rounds, new immutable scientific plans, per-question ledger/evidence and an inspectable report.
- Full backend and historical integration suites run; no production activation.
