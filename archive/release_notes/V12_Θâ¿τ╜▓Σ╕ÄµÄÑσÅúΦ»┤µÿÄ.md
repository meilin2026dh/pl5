# PL5 V1.2｜五序统一平台与ESSE融合桥接

**研究性质：** 历史过滤是用户自定义策略，输出分数不是已校准中奖概率。公平独立开奖下，保留K个不同号码的精确单期覆盖率是K/100000。

## 本次确实完成了什么

- 从 `meilin2026dh/pl5` 的 `main` 分支阅读了核心TypeScript过滤、数据源、条件体检与统计验证模块，按其当前公开接口实现本桥接层。
- 保留Python V1.1所有模块，在`research_backend/`新增 `pailie5/integration_bridge.py` 和本机HTTP服务 `integration_server.py`。
- GitHub前端以**现有原生过滤结果**作为规则真值，浏览器Worker为每条启用的规则计算100000位掩码，以LSB0位序打包（每条12500字节）。
- SHA256校验、防止外部大底越界、严格AND集合交叉校验、研究用逐刀贡献、前100注排序、预算不足的域内恢复。
- Node.js同源代理 `/api/esse/health`、`/api/esse/sculpt`，仅连接本机127.0.0.1:8765，不允许第三方转发地址，响应失败明确显示离线。
- 用户点击“将结果载入大底”后，原始规则自动停用，避免重复过滤；原有工作台功能未被删除。

## 对V1.1做出的关键防护

V1.1的`SculptSession.rank`本来可以在补足预算时从10万号码中恢复号码。对于GitHub前端的外部大底语义，这样可能把底外号码加回来。V1.2改为**只在base掩码内**做最终排序和恢复。

## 尚未实现（不可对外声称已完成）

- 跨语言对每一个复杂公式的数学独立复算。当前仅验证原生规则掩码的SHA、总量与交集，少数常见公式可作为后续独立测试夹具。
- 容错条件组`atLeast`和违规预算`violations`的等价转译。当前拒绝，避免静默改变语义。
- React/Node在用户Windows环境的实际全流程验证。已完成Python与Node语法检查；需部署以后执行GitHub `pnpm test` / `pnpm typecheck` / `pnpm build`。
- GitHub版目前的固定统计与机器学习算法自动接受为已验证算法；仍需独立前向证据与人工审批。
- Python端没有核验客户端发送的“官方数据”标签真实性；统一官方服务、历史快照签名后续加强。
- 无人值守的自主科研调度未迁入GitHub前端。V1.1科研后端保留原能力，需要单独配置。

## Windows部署（默认D盘）

1. 解压交付ZIP，在有D盘的Windows上运行 `install_to_D_v12.bat`。
2. 如果 `D:\pl5\frontend` 不存在，脚本会通过Git克隆官方GitHub项目到这个独立子目录；如果存在，脚本不会git pull或重置。
3. 若 `D:\pl5\research_backend_v12` 已存在，脚本会拒绝覆盖，以免损毁你的研究数据。
4. 安装成功后在**两个独立PowerShell窗口**分别运行根目录中的 `启动_V12_科研后端.ps1` 和 `启动_V12_五序前端.ps1`。
5. 浏览器打开开发地址 `http://127.0.0.1:5173`，点击工作台的“ESSE · V1.2融合雕塑”；生产模式可先运行`pnpm build`再`pnpm start`，打开3001端口。
6. 若原`D:\pl5`已包含V1.1核心源码，不会覆盖它，而是在子目录存放新版Python研究后端。

前端当前版本要求Node 24、pnpm 11.25.0；Python后端要求Python 3.12与uv。本交付包不会修改系统Python。

## 协议说明

请求为`pl5-esse-bridge-v1`，其中`base`与`rules[].kept`使用：

```json
{
  "encoding":"bitset-lsb0-base64",
  "bits":"<base64 of 12,500 bytes>",
  "sha256":"<sha256 of decoded bytes>",
  "count":100000
}
```

号码00000为第0位、00001为第1位、00007为第7位，00008为第二字节第一位。`rules[].kept`必须是`base`的子集；后端重新计算交集并与GitHub原生`filter()`的最终保留数量核对。

响应包含源域总量、交集保留数量、逐刀新增/重叠移除、独有贡献、Top100及随机数学基线。**mask完整哈希并不意味着TS公式独立验证。**

## 更新策略

不要在联网安装脚本中使用强制同步或覆盖 `frontend` 与`runtime`。后续建议通过单独GitHub分支提交集成补丁并运行CI测试；前端源码发生变动导致锚点不一致时，自动安装脚本应拒绝修改，而非猜测位置。
